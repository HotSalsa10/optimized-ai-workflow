## 0. In plain words

**What 6b adds.** "Ready to merge" is worked out from the checkers' own records (receipts), not from a line someone typed. A check that every number in the report to you is in a log. `/method-finish`, which takes a finished task to a pull request.

**What it stops, and what it does not.** As in the plan you approved (step6.md section 0). New since then, one line each:
- A review that asked for changes still blocks, even if it was spoiled because files changed while it ran. Only a later approving review of the same files does not clear it.
- Reviews made before 6b do not count; they are run again once.
- Claude cannot write into the folders where Claude Code keeps add-ons (mods and plugins). An add-on runs inside Claude Code, outside the safety checks.
- A broken setting for the high-risk list (a typo, a stray space) makes the task "not ready" instead of quietly shrinking the list.

**What changed from the plan you approved.** Claude decided these (A75); none is hard to undo.
- CI runs less: once on the version that goes to review, once more only if the repair changed it, and once early as a warning. Work can be saved to GitHub in between without a CI run.
- The report to you lists any changed file the plan did not name.
- After repeated failures, the report suggests one line for the incident checklist. Claude never adds it; you decide.
- If a push to GitHub fails, `/method-finish` stops and says so. The pull request's link is copied from GitHub's own answer, never typed.
- If you re-approve a plan after code exists, the "seen failing first" test run is made again by taking the code out in one commit and putting it back in the next.
- Two standing records are added: A75 (who decides what) and A76 (how CI minutes are spent).

**CI and timing.** About 190 free CI minutes are left until 1 December (your figure from GitHub's billing page, 22 November); one full run costs about 65 to 70. At most two runs fit before then. Expect 6b ready for your merge in early December, after the minutes reset, unless you buy minutes.

**Your part.** Nothing to decide now (section 7). Your merge at the end.

## 5. Known limits

step6.md section 5 still holds. Changes and additions:
- **Pruned receipts [6].** Only the newest 500 receipts per clone are kept. A pruned one reads as missing: NOT READY, with the re-run route (S14).
- **Receipts made before 6b** have no base and do not count; the reviews are re-run.
- **A receipt with no word** (cut off before its report) neither blocks nor approves. A reviewer that meant to ask for changes but was cut off is not seen; its gate must be run again before READY.
- **The `git switch -c` route [21]** (a lost fail receipt re-made at the pre-code commit) fails when method files changed on the branch after the pre-code commit (G6 refuses the switch). Then the reviews and tests are re-planned. The re-approval route (item 8) does not use it.
- **A broken method.conf on main** (a problem tagged HIGH_RISK_PATHS, or an untagged one) makes every branch NOT READY until main's file is fixed. The fix is its own small task; the owner merges it knowing done-check says NOT READY for that reason only.
- **A flaky test re-run until it passes** on the same files: the newest tester word decides; both words show in the history. A rule for flaky checks comes in step 7.
- **`gh pr edit` after a failed push** is not refused by the guard; the skill's stop line covers it by text only [P2].
- **A mod or plugin the owner installs** is not stopped [P1].
- **N1** proves a refusal inside a gate only at a pin where its case passes as written; at another pin, the case records what that pin does and RISKS #18 says so.
- **Local runs are as root** in the build session; CI runs as a user. The non-root local run before each CI push (item 27) narrows this; a CI-only failure is still possible (TESTS.md:242).
- **Backup pushes skip CI**, so a tree pushed only as a backup is never checked on Linux; no review or merge reads such a tree (A76 (3)).
- step6.md's "CI and other machines see only the verdict line" stays true until step 9.
