**What step 7 adds.**
- Templates for the nine records, REVIEW.md, the pull request text, the incident checklist and the checks file, kept short and free of any one field of work.
- `/method-setup`: about six plain questions (who decides technical choices, how much you want in reports, pace, what the project touches, how strict, which profile), plus a few short answers in your own words (what the project is, what must never go wrong, how it starts). It shows you a one-screen card of what your answers change, then writes it. A script does the writing, so the same answers always give the same files.
- Sync: copies a tagged release of the method into a project and records a fingerprint of every method file (`method.lock`). A method file changed by hand is named and never overwritten.
- Profiles: Best results (default), Balanced and Budget. They change only the model and effort of the main session (the session you talk to); the checking agents stay on Opus 5.5 at xhigh in every profile. The effort warning at session start and `/method-start` measure against your profile's effort, not always xhigh.
- The pack format: a project's own rules, checks and procedures, in places Claude Code already loads. `/method-setup` turns your "must always hold" answers into the project's first pack. No pack for any one field ships (A77).
- One core rule for scripts that write to real records outside the repo (M063): they refuse to run without a stated reason and do a dry run unless told otherwise. A small helper does it.
- Three example projects of different kinds (a terminal word game, a small website, a records keeper being adopted), with invented data, each set up and checked by a test.
- The line the method prints at session start to show it is on (`METHOD-ACTIVE`) names the installed release, such as `v0.7.0`, in place of today's placeholder `vunreleased`.

**What it stops.** Each item says what is checked, no more.
- A method file changed by hand in a project, or an extra file put in a method folder: a built-in check turns red, so the change is not ready, and sync refuses to replace the file and names it. The method's settings are checked against a copy of the release's own, so a weakened deny list stays red after setup runs again.
- Half a release: sync plans every file first, and any conflict, link, or path outside the project stops it before one byte is written. An interrupted run is finished by running it again with the same options.
- Setup answers that weaken the floor: no answer changes the checking agents' model or effort, the hooks, the deny rules or the built-in checks; the profile changes only the model and effort of the session you talk to. A test tries every combination of answers. An answer that looks like a key or password is refused before anything is written.
- A project's existing settings that would switch the method off or run their own program first (its own hooks before each tool call, rules kept from loading, a status line program and the like): the first install refuses them unless named one by one, and the card and session start name every one kept.
- A quiet change to the files that steer the method (method.conf, checks, the project's pack, CI workflows, the incident checklist, REVIEW.md, CLAUDE.md, AGENTS.md): three reviewers, all approving.
- A project's always-loaded rules growing past 8,000 bytes unseen: status says so.

**What it does not stop.**
- A sync run from a doctored copy of the method writes a lock that matches it. Step 9's CI compares the files with the real release.
- Installs and updates are written on purpose in a session where the method's hooks are off: the session must read the release, which the project's own session cannot, and hooks cannot guard their own replacement. The change is then pushed to a branch and reviewed like any other in a fresh session started on that branch, which loads the newly installed hooks and reviewers. Only if that session cannot start does the first install go to you on its card and check output alone; that exception to SPEC R4 is yours to allow (section 7).
- Pack text that weakens the floor in words. The method's rule wins on a conflict and the review reads it; no check reads meaning. The report rules that keep reports honest (status first, the five parts, exact numbers, no mods) are method rules a pack cannot change; only report length and detail are yours to set.
- A script that writes to real records without using the helper.
- Sessions where the hooks do not run (RISKS #16).

## 1. Settled choices

**S1. Copy, not plugin.** SPEC R1 stands. Rejected: a plugin or marketplace, because a cloud session "doesn't load the plugins you installed at user or local scope" (plugins/install.md [D]) and "doesn't add the marketplaces a repository lists under extraKnownMarketplaces" (plugins/loading.md [D]), and a plugin cannot carry CLAUDE.md, rules or permission rules (plugins/create.md [D]); 6b.4's guard also refuses `claude plugin install`. An `@skills-dir` plugin: exact-folder trust, cloud loading undocumented, managed policy can block it. A git submodule or subtree: a private submodule fails in cloud unless attached, and a subtree hides local edits. Symlinks: Windows needs Developer Mode, and a link can redirect writes. A78 records that the docs' "package it as a plugin" advice (features-overview.md) is set aside for these reasons.

**S2. Every project file has one owner class.** Sync and setup may act on a file only as its class allows; anything else is refused before a byte is written, naming the file and the reason (risk-first draft).

**S3. Sync is a release tool.** `scripts/release/sync.sh --source <checkout> --to <project> [--profile best|balanced|budget] [--keep KEY]... [--write]`, run from a checkout of the release it installs, so a new release always runs its own sync. Without `--profile`, an update keeps the lock's profile line; Best applies only on a first install with no lock.
- Without `--write` it prints the plan: each file as install, update, unchanged, remove or conflict. With `--write` it writes only if the whole plan holds.
- The source must be a clean checkout at an exact `v*` tag (`git describe --exact-match`, empty `git status --porcelain`). The tag is the version.
- It never fetches. A cloud session reaches the release by having the method repo attached; tests use a tagged throwaway clone.
- Refusals: a conflict (class M, K or B hash mismatch, or an extra file under a class M path); a symlink on a target path; a target outside the project; a method scalar key in the project's settings that differs from the release or profile on first install (floor keys such as `disableAllHooks`, `model`, the method's hook keys). The deny list is not among them: it is a union, which loses no release entry, and a project's own deny rule is kept.
- Refused on first install unless named with `--keep KEY` (each kept one is listed on the card): a project hook on PreToolUse, PermissionRequest, ConfigChange or SessionStart (it runs beside the guard and can rewrite an approved command, step5.md E30), or, since 7.3's fresh check (DECISIONS A79), on SubagentStart, SubagentStop or UserPromptSubmit, and since the whole-step check (DECISIONS A80) on PostToolUse, PostToolUseFailure or PostToolBatch (its output reaches the checking agents or every prompt), `claudeMdExcludes`, `enabledPlugins`, and each key in watch.pl's `@RUNS` (statusLine, apiKeyHelper and the others that run a program; one home for that list). Project hooks on other events, allow and ask rules, and other keys are kept as S6 says.
- It writes `.method/local/sync-in-progress` (the target tag) before the first file and the lock last; a re-run with that marker accepts files equal to either the old lock or the new release, then finishes.
- Files in the old lock but not in the release are removed only when their hash matches; else a conflict.
- Set in 7.3: `--source` may be left out; given, it must name the checkout sync.sh sits in (F6's measured command has none). The release's files are read from git's stored objects at HEAD, never the working copies a line-end setting could change; a link or submodule in the release, or a file outside the method's paths, is refused. A file already equal to the new release counts as unchanged, marker or not (it replaces nothing), and so do settings already holding the new release's keys; the marker is written first, removed after the lock, and a re-run that finds it says the earlier run was cut off. On an update the current keys must equal those the installed release and the lock's profile give, or the new release's; a missing settings.json is a conflict. The project folder may not be the release checkout or inside it. `--keep KEY` takes an event name (PreToolUse, PermissionRequest, ConfigChange, SessionStart, SubagentStart, SubagentStop, UserPromptSubmit) or a key name, and any other word is bad usage (exit 2); the list's one home is `Lock::refused` in `lib/lock.pl`, with `@Watch::RUNS` for the program-running keys. The managed blocks are the exact lines `# >>> method` and `# <<< method`, added at the end of the file when absent. A removal also removes the folders it leaves empty, up to the method's own. After writing, `Lock::verify` must find nothing, else exit 1. Exit codes: 0 the plan holds (written with `--write`), 1 refused or failed, 2 bad usage or no perl. After the fresh check: a relative `--to` is the folder sync is run from (F6's `--to .`; it was read from the release checkout); the marker holds the tag and the profile, and a re-run that finds it names that run's `--profile` and says it needs the same `--profile` and `--keep` (they are not taken from the marker, a file in the project that a project could commit, so `--keep` stays the person's own word); settings.json is written right after the marker, before the method files, so a run cut off between them never leaves the installed fragment newer than the settings (the re-run works out the old keys from it); a re-run that finds the marker removes each `<target>.sync-<digits>` a cut-off write left beside a path sync writes; a hook event that is not a list of groups, each an object with a list of hooks, is a conflict; a byte-order mark at the start of settings.json is read past, as session-status does; the project's settings are read with exact numbers.
- Rejected: sync.sh inside `scripts/method/`, because G6 lets any `bash scripts/method/NAME.sh` through even when it names protected paths (protect.pl:28-36, :566-580), which would make it a sanctioned way to rewrite the guard from any source folder. Fetching inside sync: the repo is private (A18), an unattached repo gets 403 in cloud [D], and tests would need the network. A three-way merge of method files: it hides local edits, against R1.

## 5. Risks and known limits

- **A forged source.** Sync from a doctored copy writes a matching lock; `method-files` then passes. Until step 9's CI compares with the real tag, the review and the owner's merge are the locks. RISKS #2 gains this.
- **The first install** is reviewed in a fresh session on its branch (S16). New RISKS #21: the fallback when that session cannot start (no gate receipts, merged on the card and check output, an exception to SPEC R4 used only with the owner's leave), and that it happens at most once per project.
- **The hookless session is now used on purpose** to write the first install and the sync half of an update: it must read the release, and hooks cannot guard their own replacement. The review then happens in a hooked session on the branch. RISKS #16 says so; step 9 proves the two-repository case live.
- **Settings keys S3 refuses** (a PreToolUse hook, `claudeMdExcludes`, program-running keys) added later by a merged change are named by session-status, not refused; the review and the owner's merge are the lock. Known limit.
- **Files the system adds under a method path** are extra, as S5 finds them on disk, hidden ones too: on macOS, Finder writes `.DS_Store` into a folder it opens (`docs/method/` among them), and `method-files` names it as not in method.lock until it is removed, and sync refuses until then; Windows' `Thumbs.db` and `desktop.ini` are the same, and an Emacs `.#name` lock file is named as a link. Known limit (set in 7.2's fix round; the other names and sync's refusal added after the whole-step check), said in why.md's M010 row.
- **The project's own env variables and skill overrides** in `.claude/settings.json` are red, as S5 compares `env`, `attribution`, `skillOverrides` and `availableModels` whole (the safer reading of S6). One in `.claude/settings.local.json` is not compared; session-status names it. Known limit, said in CHANGELOG and why.md (set in 7.2's fix round).
- **A first install keeps a project's own hooks on the events its list does not name** (Stop, Notification and the rest) without `--keep`; the list (A78 (3), widened by A79 to SubagentStart, SubagentStop and UserPromptSubmit and by A80, after the whole-step check, to PostToolUse, PostToolUseFailure and PostToolBatch, whose added context the harness saw reach a checking agent's request after each of its tool calls) names the events that run beside the guard or before it and those whose output reaches the checking agents or every prompt. A project's formatter on PostToolUse is kept by naming it, and session-status then names it in every session. The review and the owner's merge read the others.
- **Numbers in the project's settings** are written in their shortest exact form when sync rewrites the file: `1.0` becomes `1` and `1e3` becomes `1000`, the same value; long integers keep every digit. Known limit (7.3's fresh check).
- **The .gitattributes method block goes at the top** of a file that has none (since the whole-step check), so the project's own later line-end rules win, as git takes the last line that matches: a project line on `*` that asks for `eol=crlf` then reaches the method's files too (`-text` only stops git converting, so the stored LF files stay LF). That fails closed: method-files names a method file with CRLF line ends, and method.lock with a CR is refused. Known limit.
- **A project's `permissions.defaultMode`** is kept by sync and named by nothing. Measured after the whole-step check at 2.1.316 and 2.1.319 with the harness's fake: `bypassPermissions` and `auto` from the project's settings have no effect (the session starts in `default`); `acceptEdits` takes effect, and a PreToolUse hook's refusal still holds under it.
