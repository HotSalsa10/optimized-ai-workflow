# DECISIONS

Facts that outlive the work: choices, rejected options and traps. Settled decisions are not reopened without new evidence. Each entry says why. Sources are listed in docs/research/.

A1. The method lives inside each project's repo, copied from this repo and kept in sync by releases. Not a plugin, not ~/.claude. Why: cloud sessions load only what is committed in the repo and do not install plugins a project enables (Claude Code docs, cloud environments page).

A2. Default model policy: Opus 5.5 by full ID (`claude-opus-5-5`) for every role, set in project settings with `model`, `availableModels` and `enforceAvailableModels`. Why: in a host-managed cloud session, `CLAUDE_CODE_SUBAGENT_MODEL` and its FORCE switch are dropped from project settings, while `model` plus `availableModels` forced Haiku-pinned and Haiku-requested agents onto Opus (measured by token accounting, Oct 2026).

A3. Effort, "Best results" profile: xhigh for FULL builds and every checking agent. This departs from Anthropic's default advice (start at medium; keep xhigh and max for measured gains). Why: the owner does not steer code, errors in money and data are silent, Anthropic describes xhigh as suited to long unattended coding, and Cloudflare's randomized test found a reviewer at high caught 58% more serious findings than at medium. Balanced and Budget profiles follow Anthropic's defaults.

A4. Never set `CLAUDE_CODE_EFFORT_LEVEL`. Why: it silently overrides `--effort`, `/effort` and agent frontmatter, flattening every role to one level (measured). A top-level `effortLevel` in user settings is ignored by Opus 5.5 (docs); the project file sets effort instead.

A5. The server-side advisor is off (`CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`). Why: under the Opus allowlist it is Opus advising Opus, its advice is encrypted and unreadable to the owner, every checking agent inherits it, and Anthropic's best measured pairing was within run-to-run noise.

A6. One agent builds; subagents only check or look things up. No cheap worker agents by default. Why: Anthropic's measurements, an independent single-task test and the shared YouTube experiment all found delegating one connected build gave no quality gain and was slower.

A7. Review design: a blind fresh-context reviewer and a security-checker, once per build increment; at most 3 rounds, then re-plan; later rounds review only the changes since the last reviewed version; every finding gets a disposition (fixed with its proving test, wrong, intentional, not worth it); flag the whole bug class; never repeat a posted finding; unproven serious or security findings go to an unresolved list, never dropped; Deep review (several independent finders and a vote) for high-risk paths. Why: Anthropic's Claude Code team measured mean reviews to pass falling from 2.08 to 1.32 with these rules; reviewers prompted to find gaps usually report some even when the work is sound.

A8. People who read code add a review layer; they never replace the reviewer agents. Human reviewers look at intent, business rules, design and risky paths first, and at the AI findings after. Why: layered checks miss different things; a study found people shown an AI review mostly checked what it flagged.

A9. For an owner who does not read code, high-risk changes get Deep review, written sign-off of expected results by the person with authority (accountant, lawyer, client), the non-AI checks, a test copy and an undo plan, and a recommended paid human expert review before go-live. Without that expert, the change ships only after the owner accepts a written note saying it had no human code review. Why: Anthropic never lets automation fill a human slot on its riskiest code; no source shows a non-programmer safely relying on AI review alone.

A10. Verdict words: APPROVE, REQUEST CHANGES, REJECT (wrong approach, re-plan), ESCALATE (a person must decide). Commit trailer values: `approve`, `request-changes-resolved`, `request-changes-open - <what>`, `not-required - <reason>`. The trailer is the last paragraph of the commit message, on one line.

A11. LIGHT tasks relax five things: one review round; no new guards unless something failed; no planting or mutation testing; no planner (1 to 3 acceptance lines instead); no reporter unless there are [EYES] or [CHECK] items. LIGHT never drops the reviewer, the security-checker, the scripted checks or the merge check. Why: the owner's original three relaxations plus two the critics showed were safe; owner approved.

A12. The separate supervisor session is replaced by a reporter agent that re-derives claims, plus the scripted merge check. `/supervise` stays available. It becomes required again if overstatements get through. Owner approved.

A13. "Give the owner a ! command" becomes "fixed scripts the owner runs on their own computer". Live writes go only through reviewed scripts with a dry run by default. Owner approved.

A14. The method is flexible through `/setup`: questions about the person and the project. Answers change who does what, pace and strictness, never the floor (SPEC R4).

A15. Three profiles: Best results (default), Balanced, Budget.

A16. New projects and big features start with a design stage: an architect agent, an independent design review, a design card for the owner in business terms, versions checked against live package registries, and a walking skeleton built first.

A17. Scope: solo people, whether they code or not, and small teams. No company-specific features.

A18. This repo is private for now. MIT licence included so going public is one switch. Nothing may assume the repo is private.

A19. CI: Linux on every change; Windows (Git Bash) and macOS before each release and on demand. Why: a private repo's free CI minutes run out faster on Windows and macOS runners.

A20. No head-to-head benchmark against stock Claude Code (owner decision: the design rests on good evidence). The reviewer test from the original requirements and the planted-defect proofs stay.

A21. Improvement loop by hand: `/research <link>` any time and `/research-update` every 2 to 4 weeks. No scheduled watcher (owner decision).

A22. Commit attribution is off. No Co-Authored-By or session-link lines (owner rule).

A23. Hook scripts are bash plus perl with JSON::PP, run in shell form. Node is not assumed. Why: node is not installed by default; perl ships with Git for Windows, macOS and Linux.

A24. The commit-msg hook that refuses a missing trailer is not shipped. Why: the trailer is generated from receipts, so nobody types "approve".

A25. Rejected: a weekly watcher; `/autocompact` on top of the autocompact percentage; full ASD-STE100 writing; explainer videos; third-party usage mods; plugin-only distribution; the ECC plugin; `/code-review`, `/goal` or the advisor as a gate.

A26. Writing rule that had a measured effect: keep every hedge and every number exactly, with currency, sign and period.

A27. For now the method is for the owner alone, on Linux (including Claude Code cloud sessions). Linux is the only system that must pass. The Windows and macOS runs of A19 wait until the method is used on those systems or shared. The scripts keep following the portability rules, so that later run is a check, not a rewrite. Why: owner decision; it saves Windows and macOS minutes, which cost more.

A28. Each project keeps one incident checklist, `docs/incident-checklist.md`, and the review packet gives it to every checking agent (M032). The packet reads it from the merge base, so a change cannot weaken the list it is checked against; an edit to it shows in the diff. Why: M032 names one project list, and no record set up a list per agent; reading it from the base stops a change from grading itself against a list it wrote.

A29. The review packet has no size limit. Why: no rule asks for one; the plan's 80 KB cap would have refused this repo's own step 1b reviews (diffs of 85 KB and 121 KB), and M112 keeps migrations whatever their size. A limit enters the rule map with its reason first.

A30. status.sh judges commit trailers only on main's first-parent history: the commits after `VERDICTS_FROM` in `.claude/method.conf`, or, when that is not set, every commit from the oldest one there that has a trailer line. Why: what landed on main is what the record must show; commits on a task branch are work in progress, and done-check (step 4) checks a change when it merges. Older commits are accepted by moving `VERDICTS_FROM` in a reviewed change, never by rewriting main. This depends on every commit that lands on main ending with the trailer itself, so a merge or squash merge must pass the trailer through: GitHub's squash merge adds a `---------` line and Co-authored-by lines after it when the commits' authors differ from the pull request's author, and status names that as the cause.

A31. M050 ("check what a fresh clone gets") is met by run-checks' fresh-clone check together with CI's clean checkout, not by running the checks in a throwaway clone. Why: a project's checks need installed dependencies that a bare clone lacks, so a throwaway clone would fail for the wrong reason. The fresh-clone check fails on files under PRODUCT_PATHS that git ignores (here, but not in a clone) unless LOCAL_ONLY says a clone is meant to lack them, and CI runs the same checks from a clean checkout. The CI half reaches a project with step 9's CI templates; until then a project has the fresh-clone check alone.

A32. status.sh reports with three words: PASS, LOOK and SKIPPED, never FAIL. Why: status reports and never blocks (M003); LOOK asks a person to look, and its exit code 1 says the same to a caller. run-checks.sh keeps PASS, FAIL and SKIPPED, because its FAIL does block.

A33. Until review receipts exist (step 5), done-check takes a change as ready to merge only when its head commit's verdict line is `approve`. verdicts.txt holds this as its own kind, `ready`, apart from the grammar (`trailer` values stand alone); every `ready` word is also a `trailer` word. Ready words: `approve`. Why: SPEC R4 has the review run and approve, and `request-changes-resolved` means the last review asked for changes and no review approved the fixes (step 3 closed fixes that were checked but not re-reviewed as `request-changes-open`; plan v3 had "main accepts only approved work"). Reading a typed line for now does not reopen A24: done-check is not a commit hook, nothing gates a merge on it in step 4, and its READY line says the line is typed and not yet backed by a receipt.

A34. A check that runs only in the other place (runs_in `ci` locally, `local` under CI=true) never counts toward READY: done-check's elsewhere condition fails until it can read that place's result (step 9). Why: M089; a READY with exit 0 would let a merge through while a product check ran nowhere done-check can see. This also closes CI=true set by hand. The cost: a project with such a check is never READY locally before step 9.

A35. done-check matches a run-checks log to HEAD by files and parents, not by commit id: the log's commit is HEAD, has HEAD's tree and parents (HEAD amended to add the verdict line), or has HEAD's tree and is an ancestor (an empty verdict commit on top). The newest such log from the same place decides, complete or not. Why: the verdict line is written after the review, which needs the check output first (review-packet --checks), so matching the commit id would void every run; step 5's receipts are keyed to the files too.

A36. "The files on disk are the commit" (lib/tree.pl) accepts a file that differs from the stored bytes only when it equals what git's own checkout writes from the commit's own attributes: git is asked (cat-file --filters) with the system and personal attribute files off, attributes read from the commit, this machine's line-end settings pinned off and every filter driver off. git 2.42 is needed, and `.git/info/attributes` must hold no rule (git reads it even then); otherwise no conversion is accepted. Why: a committed `eol=crlf` (Gradle, `*.bat`, the method's own `*.cmd`) or `ident` file is never byte-equal on Linux, so a byte-only rule would leave such projects never clean; but a CR that only this machine's settings write turns `set -e` off in a shell script while git status sees nothing, which is the edit this rule exists to catch. Git LFS content on disk counts only where the commit's own attributes mark the path `filter=lfs`, under the same conditions; otherwise a clone gets the pointer. run-checks and done-check also compare each checked-out submodule with the commit the parent records for it, and turn off a submodule's own filters when git status reads it. A file that still holds the stored bytes counts as the commit even when the commit's own .gitattributes asks for a conversion (an eol rule added in the change): a fresh clone then gets other bytes, which CI's clean checkout sees (step 9); refusing it would turn every LF file under a committed eol=crlf rule into a change until it is checked out again. A symlink written as a plain file (core.symlinks=false, Git for Windows without symlinks) is a change, so the packet and done-check refuse such a checkout. Where the working tree's file system tells case apart, every git call made through Git::run pins core.ignoreCase=false (a true value there would hide an untracked case twin of a tracked file); where it folds case, git's own setting stays, so ignore and attribute patterns match as git matches them (review round 4 found a pin everywhere gave false NOT READY results there). The working tree decides, not the git folder: a worktree on a volume that tells case apart, with its git folder on one that folds, still gets the pin (the check of the last fix round).

A37. done-check judges a change to VERDICTS_FROM by what it makes status stop judging: the commits on main without a valid verdict line that leave the range (Verdicts::judged, shared with status). None: it passes and names the move. Some: it passes and names them on the READY line. Why: A30 accepts older commits by moving VERDICTS_FROM in a reviewed change, and the verdict condition already asks for that review; refusing every move would block A30's route and every adoption (step 7). VERDICTS_FROM is read from each committed .claude/method.conf as status reads it: a line with a problem leaves its key unset, and a file that is not a regular one sets nothing, so a change that fixes a broken file on main can be ready. HEAD's value must equal the one in the file on disk, which status reads: a .claude kept in a submodule, or a method.conf stored through Git LFS or another filter, holds a value the commit does not, and would let a move go unjudged (review round 3). Main's value is read from main's stored file; where that cannot be what status reads on main (.claude a submodule, the file a Git LFS pointer, or main's own .gitattributes giving it a filter or an encoding), verdicts start could not check, and fails (review round 4). The same holds for HEAD's file, which status reads once the change is checked out (an encoding rule added in the change). Where git cannot read a commit's own attributes (git older than 2.42, or rules in .git/info/attributes), a .gitattributes on the path that names a filter, an encoding or a macro counts as such a rule.

A38. done-check has no `--base`: main is lib/git.pl's Git::main_ref, which does not take origin/HEAD when it names HEAD's own branch or its namesake on origin. A branch's upstream is no reason to skip it: `git checkout -b feat origin/develop` makes the default branch the upstream (review round 1 found the false READY that rule gave). Main is read from origin, or from the only remote when none is named origin (`git clone -o up`); with several remotes and none named origin there is no main. A local main or master counts only when there is no remote at all: git fetch never moves it, so it can be behind the main that was fetched (review round 3 found a false READY that way). Why: M108 names main; a caller-chosen base, or an origin/HEAD that a clone of a working copy or `git remote set-head` points at the task branch, would check the change against itself. Main's ref counts only when the remote's fetch settings name it, so that git fetch moves it: a ref fetched by hand into a single-branch clone is never moved again (the check of the last fix round found a false READY that way), and done-check advises git remote set-branches --add. A remote counts only with a URL (a remote.origin.* setting alone in a personal settings file is not one); remote-tracking branches with no remote set up (a fetch by URL) also leave main unknown, rather than falling back to a local main.

A39. M044 is split in two. M044 keeps "break the code under test on purpose" (mutate-changed.sh, step 4b); its second half becomes M122, "every input a plan's tests use takes at least two values, one of them not the default", homed in done-check.sh at step 6, where `--ready` reads the plan's parameter matrix (plan v3 section 10). Why: mutation shows a never-varied input only indirectly, as survivors on changed lines that use it; inputs used on unchanged lines, or by operators the mutator lacks, stay unseen. One rule, one home (M111). M118 was taken.
A40. mutate-changed.sh breaks code with a text mutator of its own (operators any language shares: comparisons, shell tests, logic, booleans, integers), not with mutmut or another per-language tool, and mutates the working tree itself, not a throwaway copy. Why: a per-language tool needs installing (A23) and leaves the languages without one unchecked, and wording in method/ is field-neutral; a throwaway copy lacks the installed dependencies the checks need (as for A31). The checks run against each mutant are the ones the project names in MUTATION_CHECKS (its fast tests), never all checks; this replaces plan v3's MUTATION_CMD. Only files whose disk bytes are the stored blob are mutated: writing blob text over a file git's checkout converts, or over Git LFS content, would change it. There is no --base: the base is the merge base with main (A38). A mutant runs with the session's rights, so a file or line that names one of a fixed list of delete and move commands gets none (a delete written any other way is not recognised, even on its own line): a shell script, make file or batch file that names one anywhere is skipped whole (its guard can sit on another line), and in any other file the line that names one gets none (RISKS #13; review round 1 of 4b.2 found a per-line rule for && and || only let != turn a guarded rm around, and round 2 found git options and $(RM) that hid the command). The screen shows the plan without a line's text, and a number other than 0 and 1 only by its length (round 2: a phone number in groups of two digits). Two merge bases stop it (merge main first).
A41. The lock run-checks and mutate-changed share, and the limited runner for mutate-changed's checks (step 4b.3a). The lock, and a mutate run's journal, live in git's own folder for the working tree (lib/runstate.pl: `git rev-parse --git-path method-run.lock` and `method-mutate-journal`), not in .method/local. Why: a check that runs git clean -fdx deletes .method/local, and with it a journal while a mutant is on disk; and nothing is written into the working tree, so nothing needs ignoring. run-checks holds the lock shared for its whole run, mutate-changed exclusively. Why: a journal exists only while a mutant is on disk, so "refuse while a journal exists" leaves the gaps between mutants, and a run-checks run there logged a clean pass over a mutant that was put back before it ended (shown when 4b was designed). A holder keeps trying for 5 s before it says busy, so a status probe's brief shared hold, or the watchdog of a cut-off run, does not read as busy. Each of mutate-changed's checks runs as the leader of its own process group under a watchdog: a fork of the caller, in a process group of its own, that ignores the stop signals, sets every other signal back to its default, keeps none of the caller's descriptors but the lock, has a name of its own, and is the one place that stops the group (TERM, KILL 2 s later when any of it is left) when its caller closes the pipe or ends in any way, kill -9 included (the pipe closes, or the watchdog's parent changes); so a cut-off run's lock stays held until its checks are stopped. Why: the critique of the 4b.3 design showed that a watchdog inside the check's group dies from its own TERM, and that one which exits when the check ends leaves what the check left behind unguarded; review round 1 of 4b.3a showed that one in the caller's group dies with it under a KILL to that group (timeout -s KILL). A fast finish (the signal path) kills the watchdog and the group at once rather than waiting for the group to be gone, as a killed check's children can stay zombies for seconds. status keeps its own time-limited runner for the read-only tools whose output it reads; run-checks keeps run_to_file, as its checks have no time limit.
A42. How a run of mutants starts, writes and ends (step 4b.3b). The lock comes first, then the signal handlers, then recovery, and only then the settings, so a setting changed after a cut-off run never keeps its mutant on disk. One write function: a temp file next to the file (a name the journal records, so every writer, recovery included, uses the same one), synced, given the file's mode and a time that is the next whole second, or one past the file's own, renamed over it only while the file still holds what the run expects there (else the run stops and the edit stays); it waits at most 1 s when times run more than 2 s ahead, and never writes an old time back. Why: a cache keyed on the time in whole seconds and the size (Python's .pyc) would otherwise take a mutant for the original, and a build tool that compares sub-second times (make) would take a mutant written in the same second as a build for older than it (review round 1 of 4b.3b); a session may edit while a run goes on in the background. One restore rule (the mutant is put back; the original is left; a file changed on top of its mutant is left as it is once the mutant's line is gone from it; anything else is refused and the journal stays, saying where the mutant is, which the journal records, and that the way out is to undo that one change: a copy of the file, or a diff of it, would bring the mutant back; review round 2 of 4b.3b) and one release rule (the journal goes only when HEAD, the index and any stash made during the run do not hold the mutant, or its line: an edit made on top of the mutant and then staged, committed or stashed keeps the line, not the bytes; the journal keeps that line's SHA-256, and that of the line with the lines around it, and a blob holds the mutant when it has more such lines, alone or with those lines around them, than the original; a copy of the mutant's line counts as the original's own only while its lines around it are the original's, and any other copy is "cannot tell", which keeps the journal (review round 3 of 4b.3b and the check of its fixes); recovery goes on only while HEAD is the start, one after it, or one with the journal's files as they were then (a HEAD older than the run cannot hold its mutant and is told to check the start out; any other is looked at for the mutant first; what is left is RISKS #15), no git operation is in progress, no autostash a merge left holds it, and every git command it asks answered: a git rev-parse that ends other than "there is none" is "cannot tell", review round 2 of 4b.3b) serve the round, a signal, an error and recovery. A round stops the check's group first, then puts the file back: a leftover could otherwise write the mutant back after it. No run during, and no recovery during, a merge, rebase or other git operation, whose autostash can hold a mutant. Each check's limit is 3 times its run A time plus 30 s; --minutes (default 8: a foreground tool call allows 10) stops starting mutants that might not end in time. A native Windows perl is refused (no fork, no process groups). A run of mutants never exits 0 until 4b.4: all killed is SKIPPED kills-unchecked, since kills are what a broken check fakes.
A43. How a run of mutants trusts its kills (step 4b.4). A kill is a check failing on a mutant, which a broken check fakes, so three runs without a mutant stand around the mutants: run B repeats run A (a check whose result does not repeat, because something a run leaves behind changes the next one, makes every result untrustworthy: exit 2); the control run adds one line end at the end of every file that will get a mutant, through the same write function and journal as a mutant, and a check that does not pass it (a "build is current" check that compares times or bytes, a snapshot of the files, anything that fails on any change; a check that compares built output, which one more line end does not change, passes it) cannot show it noticed a mutant, so it is not used and is named, as is a check SKIPPED in run A (no count, a count of 0); run C after the last mutant (a round that left something behind: exit 2). No usable check left is SKIPPED no-usable-check. B, C and the control run must fit --minutes before the first mutant, and each mutant starts only when it and run C still fit. PASS (exit 0) only when every mutant ran and was killed and nothing the branch changed under MUTATE_PATHS was left out but the method's or git's own files: a pass over a change whose risky lines were never mutated (kept out by the delete words, or a file skipped as converted, LFS, too large, not UTF-8 text, not a regular file, or a deleting script) would claim more than it showed (reviews of 4b.2, I-b and S3-7), so those are named and the result is SKIPPED not-all-mutated. Kills are counted for the check that made them. Runs A, B and C compare the files, HEAD, the branches and tags, and the stash with the start, as each round does. The control run's journal names each file just before it is written, so a file the run did not write is never put back (an edit made to it, even one equal to the line end, is kept; review of 4b.4, round 1); it names no line to look for, as its edit is not a mutant, so an edit made on top of the line end is left as it is, and the line says that line end may still be there. Every file a journal names is tried when files are put back, in the run and in recovery: one that cannot be does not keep the others from it (the line names 10 refusals, then how many more). Whether the file system folds case is asked inside the working tree (its .git against .GIT, links not followed), so a link with the top folder's flipped name next to it cannot make a product Checks/ count as the method's (review of 4b.4, round 2). Where the file system keeps letter case, a changed file named like the method's or git's own in another case (a product folder Checks/) is not theirs, so it is named and the result is SKIPPED not-all-mutated, never PASS.
