# RISKS

Each risk says what could go wrong, what reduces it, and what is left.

1. Opus reviews Opus's work, so both can share a blind spot. Reduced by expected results from outside the model, mutation testing, a non-AI security scanner, Deep review on high-risk paths and a human expert before high-risk go-lives. Left: nothing closes it fully.

2. Guards that match shell commands can be bypassed by a model that is set on it. Reduced by checks that run outside the agent (CI, hashes of locked files, receipts bound to the exact version). Left: CI checks that receipts are consistent, not that they are authentic.

3. A Claude Code update renames a setting or changes behaviour. Reduced by status.sh, which compares the running Claude Code with the floor in `method/scripts/method/REQUIRES` (SPEC, Supported versions). To be reduced further by the hook test harness (step 5) and a compatibility check in every `/research-update` and before every release. Left: breakage between checks, and an update above the floor that changes behaviour.

4. The repo is private. Without a paid GitHub plan, GitHub does not enforce branch protection, so the merge button works even when checks are red. To be reduced by the guard hook refusing merges by Claude (step 5) and by the owner's release stop. Until step 5, nothing in the repo stops a merge; only Claude Code's permission prompts and the owner do. done-check.sh computes readiness, but nothing runs it before a merge until step 5's guard and step 9's CI.

5. Some research was read only through search summaries, because the cloud environment blocks many sites. The main conclusions rest on sources read in full; details may move. Reduced by `/research-update`.

6. On the Pro plan, usage limits can stop work mid-task. Reduced by checkpoints that save state to files, and a rule that a limit never justifies skipping a check.

7. The method itself grows until checking costs more than the work (the owner's 20-line rename incident). Reduced by tiers, context budgets enforced by tests, and pruning rules that no longer earn their place.

8. CI minutes on a private repo run out. This happened during Release 1 step 1: the account had used its included Actions minutes, so GitHub started no machine for any run. Reduced by running Windows and macOS only before releases and on demand, because their minutes cost more than Linux minutes. Left: no CI until the minutes renew on 1 November.

9. While the Actions minutes are used up (risk 8), CI proves nothing: every run ends in about 3 seconds with no machine and no logs. The same checks pass locally on Linux, but nothing has run on macOS or Windows yet; for now only Linux must pass (DECISIONS A27).

10. The secret scan reads the current files, not git history (a by-hand scan of the whole history during step 1 was clean), so a secret added and removed within one push is not seen. A history scan is planned for Release 2.

11. The review packet trusts its caller and runs from the change itself. It also trusts the session it runs in: PATH, git and perl, and git's own environment (GIT_EXEC_PATH among it). The caller picks `--base` and `--since`, so commits could be left out of a review; local branch and remote-tracking refs can be moved by whoever can write to `.git`, so the safest `--base` is a full commit id taken from a fresh fetch or a trusted record (the commits after the merge base are checked against their ids, so a commit changed by hand cannot move it); review-packet.sh, its helpers and verdicts.txt run from the checked-out change, so a change to them packages itself. An uncommitted edit to them, hidden from git by an index flag, does the same, because the edited builder could also skip its own check. Lockfile changes are listed by line count only, so the security check sees a swapped package source only if it opens the file. Reduced by the merge base, the "in doubt" fallback and the tests. The same holds for run-checks.sh, status.sh, done-check.sh (with lib/done.pl and lib/tree.pl) and `checks/*.tsv`, which also run from the checked-out change, locally and in CI, and trust the session the same way: a project's check commands and count patterns are project code, reviewed like tests, and run with the user's rights and no sandbox; run-checks' log and screen are written by the code being checked, so they are local claims, not evidence; its log sits in a git-ignored folder anyone in the session can write, and deleting or renaming one log removes a failed run from what done-check reads; and done-check's READY rests on that log and on a verdict line the author typed, so a change to done-check, its libraries, verdicts.txt or the inputs it reads grades itself. Local branch and remote-tracking refs are local files too, so main is what the last fetch left. Closed when receipts record the base and the last reviewed version (step 5), the review machinery runs from the main branch in CI (M118, Release 2), and the security checker's dependency duty is written (M030, step 6).

12. This repo's own steps closed at the 3-review-round cap without an approving verdict (their commits say `request-changes-open`), so its branch is NOT READY under its own done-check. That is the truth under SPEC R4, not a defect: done-check never turns an unapproved version ready, and a person's approval does not replace the review's. The owner decides how this repo merges.

13. mutate-changed.sh (step 4b.3 on) runs the project's checks against code it has broken on purpose, in the working tree, with the session's rights: a mutant can turn a guard around and make a check delete, move or overwrite files it was meant to keep. Reduced by its plan (step 4b.2): a shell script, make file or batch file with a line that names one of a fixed list of delete and move commands gets no mutant, and in any other file that line gets none; the words are listed in mutate-changed.sh's header. Left: the list is words, not a parser, so a delete, move or overwrite written any other way (a command or call not on the list, cp over a file, a helper of the project's own, a command split over lines without a line-end backslash) gets mutants, even on the line with its guard; and outside shell, make and batch files a guard on another line than its delete gets mutants, unless a line-end backslash joins the two. Run it in a session or container whose working tree you can lose, and commit first.

14. The lock that run-checks and mutate-changed share, and a mutate run's journal (lib/runstate.pl), live in git's own folder: anyone in the session can delete them, and the lock then guards nothing. A process a check starts in a group or session of its own (setsid, setpgid, a detached spawn, a container) is not stopped when the check is, and neither is what a check left behind when a harness kills the whole process tree, the watchdog with it. On NFS, flock is a per-process lock that a fork does not share, so a cut-off run's watchdog does not hold it while it stops the checks. A group number taken again in the instant between a check's end and its stop could get the stop signal. Reduced by: the watchdog is in a process group of its own, ignores the stop signals and has a name of its own, so a kill aimed at mutate-changed (its process group, KILL included, or its name) leaves it to stop the checks, and it also stops them when its parent changes; recovery (step 4b.3b) waits for a cut-off run's checks and names their group.
