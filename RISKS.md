# RISKS

Each risk says what could go wrong, what reduces it, and what is left.

1. Opus reviews Opus's work, so both can share a blind spot. Reduced by expected results from outside the model, mutation testing, a non-AI security scanner, Deep review on high-risk paths and a human expert before high-risk go-lives. Left: nothing closes it fully.

2. Guards that match shell commands can be bypassed by a model that is set on it. Reduced by checks that run outside the agent (CI, hashes of locked files, receipts bound to the exact version). Left: CI checks that receipts are consistent, not that they are authentic.

3. A Claude Code update renames a setting or changes behaviour. Reduced by status.sh, which compares the running Claude Code with the floor in `method/scripts/method/REQUIRES` (SPEC, Supported versions). Reduced further by the $0 harness (step 5.2, A49), which runs the real client at the floor and at the tested version on every Linux change: its cases fail when a hook stops firing as recorded, and a tool the client starts to offer fails it until tests/harness/tools.txt names it. To be reduced further by a compatibility check in every `/research-update` and before every release. A settings value of a type the client rejects makes it skip the whole settings file, hooks and all, with no warning in a -p run (measured, 2.1.316 and 2.1.319); tests/settings.test.sh checks every value's type, and the harness keeps checking that behaviour. Left: breakage between checks, and an update above the floor that changes behaviour.

4. The repo is private. Without a paid GitHub plan, GitHub does not enforce branch protection, so the merge button works even when checks are red. Reduced by the guard, which through Release 1 refuses Claude every way to land a change (DECISIONS A46), so the owner's merge on GitHub is the only lock outside the session; by done-check, which since step 6b works out "Ready to merge" from the gates' receipts and the task's plan, and which `/method-finish` runs before it opens the pull request and copies into it; and by the owner's release stop. Left: nothing on GitHub stops a merge, so a change whose CI is red or whose done-check says NOT READY can still be merged by the owner's click; where the hooks do not run (risk 16), nothing in the session stops Claude merging; and nothing runs done-check on GitHub before step 9's project CI. Planned: GitHub branch rules in Release 2 (ROADMAP Track 2), when landing by Claude can return.

5. Some research was read only through search summaries, because the cloud environment blocks many sites. The main conclusions rest on sources read in full; details may move. Reduced by `/research-update`.

6. On the Pro plan, usage limits can stop work mid-task. Reduced by checkpoints that save state to files, and a rule that a limit never justifies skipping a check.

7. The method itself grows until checking costs more than the work (the owner's 20-line rename incident). Reduced by tiers, context budgets enforced by tests, and pruning rules that no longer earn their place. Since step 6, tests/budget.test.sh holds the rules every session loads to 8,000 bytes and the agent and skill descriptions to 3,000 (6,334 and 2,178 at step 6.5), and the prompt lint keeps the method's text plain (DECISIONS A73). Left: the budgets bound the words, not the checking each change asks for.

8. CI minutes on a private repo run out. This happened during Release 1 step 1: the account had used its included Actions minutes, so GitHub started no machine for any run. Reduced by running Windows and macOS only before releases and on demand, because their minutes cost more than Linux minutes. Left: no CI until the minutes renew on 1 November.

9. While the Actions minutes are used up (risk 8), CI proves nothing: every run ends in about 3 seconds with no machine and no logs. The same checks pass locally on Linux, but nothing has run on macOS or Windows yet; for now only Linux must pass (DECISIONS A27).

10. The secret scan reads the current files, not git history (a by-hand scan of the whole history during step 1 was clean), so a secret added and removed within one push is not seen. A history scan is planned for Release 2.

11. The review packet trusts its caller and runs from the change itself. It also trusts the session it runs in: PATH, git and perl, and git's own environment (GIT_EXEC_PATH among it). The caller picks `--base` and `--since`, so commits could be left out of a review; local branch and remote-tracking refs can be moved by whoever can write to `.git`, so the safest `--base` is a full commit id taken from a fresh fetch or a trusted record (the commits after the merge base are checked against their ids, so a commit changed by hand cannot move it); review-packet.sh, its helpers and verdicts.txt run from the checked-out change, so a change to them packages itself. An uncommitted edit to them, hidden from git by an index flag, does the same, because the edited builder could also skip its own check. Lockfile changes are listed by line count only, so the security check sees a swapped package source only if it opens the file. Reduced by the merge base, the "in doubt" fallback and the tests. The same holds for run-checks.sh, status.sh, done-check.sh (with lib/done.pl and lib/tree.pl) and `checks/*.tsv`, which also run from the checked-out change, locally and in CI, and trust the session the same way: a project's check commands and count patterns are project code, reviewed like tests, and run with the user's rights and no sandbox; run-checks' log and screen are written by the code being checked, so they are local claims, not evidence; its log sits in a git-ignored folder anyone in the session can write, and deleting or renaming one log removes a failed run from what done-check reads; and done-check's READY rests on that log, on the task's plan and on the gates' receipts (since step 6b.1; before it, on a verdict line the author typed), all local records, so a change to done-check, its libraries, verdicts.txt or the inputs it reads grades itself. The receipts now record each packet's base, and done-check counts a review only when its base is the merge base or chains back to it, so a review built from a later `--base` or a `--since` that skips commits no longer counts; a receipt is still a local file (RISKS #2), kept in this clone only. mutate-changed.sh and lib/mutate.pl run from the change too, and its PASS covers only what the change's own MUTATE_PATHS and MUTATION_CHECKS name, so a change that narrows them (or a check's command) grades itself; the review packet shows that change. Local branch and remote-tracking refs are local files too, so main is what the last fetch left. Closed when receipts record the base and the last reviewed version (done in step 6b.1), the review machinery runs from the main branch in CI (M118, Release 2), and the security checker's dependency duty is written (M030, written in step 6.2, in method-security-checker.md).

12. This repo's own steps closed at the 3-review-round cap without an approving verdict (their commits say `request-changes-open`), so its branch is NOT READY under its own done-check. That is the truth under SPEC R4, not a defect: done-check never turns an unapproved version ready, and a person's approval does not replace the review's. The owner decides how this repo merges.

13. mutate-changed.sh runs the project's checks against code it has broken on purpose, in the working tree, with the session's rights: a mutant can turn a guard around and make a check delete, move or overwrite files it was meant to keep. Reduced by its plan (step 4b.2): a shell script, make file or batch file with a line that names one of a fixed list of delete and move commands gets no mutant, and in any other file that line gets none; the words are listed in mutate-changed.sh's header. Left: the list is words, not a parser, so a delete, move or overwrite written any other way (a command or call not on the list, cp over a file, a helper of the project's own, a command split over lines without a line-end backslash) gets mutants, even on the line with its guard; and outside shell, make and batch files a guard on another line than its delete gets mutants, unless a line-end backslash joins the two. Run it in a session or container whose working tree you can lose, and commit first.

14. The lock that run-checks and mutate-changed share, and a mutate run's journal (lib/runstate.pl), live in git's own folder: anyone in the session can delete them, and the lock then guards nothing. A process a check starts in a group or session of its own (setsid, setpgid, a detached spawn, a container) is not stopped when the check is, and neither is what a check left behind when a harness kills the whole process tree, the watchdog with it. On NFS, flock is a per-process lock that a fork does not share, so a cut-off run's watchdog does not hold it while it stops the checks. A check can stop or kill its own watchdog (it is the check's parent and runs as the same user): stopped, it keeps the lock held, so run-checks says busy and recovery waits, until someone kills it (fails closed); killed, it leaves the check unguarded. On Git Bash, programs a native Windows program starts are outside the check's process group (reasoned, for the Windows review, A27). A group number taken again in the instant between a check's end and its stop could get the stop signal. Killed together in the instant after a check starts, before its group is written into the journal, mutate-changed and its watchdog leave a journal that names no group, so recovery cannot wait for that check. Runs A, B and C write no journal, so when mutate-changed and its watchdog are both killed during one of them, nothing names the check left running, and --recover has nothing to do.

15. After a cut-off run (kill -9), a session that edits a file on top of its mutant can, in narrow ways, hide the mutant from recovery, which then says RECOVERED and leaves it: by changing the mutant's own line further; by deleting a twin of the mutant's line so that the mutant takes on that twin's own lines around it (shown by the last check of step 4b.3b); or by committing it on the branch the run was on and then leaving that branch. Reduced by: recovery looks for the mutant's line, and for its line with the lines around it, in the file, HEAD, the index, the stashes and MERGE_AUTOSTASH, and refuses wherever it cannot tell; it goes on only from the commit the run started on or after it, looks at a HEAD made since the run first, and its check-out advice says to look at commits made on that branch since; mutate-changed.sh's header says not to edit files while a run is going. Planned: an exact way to find the mutant in an edited file (a three-way merge of the mutant's own change against it, not line counts), ROADMAP Track 2. Reduced by: the watchdog is in a process group of its own, ignores the stop signals and has a name of its own, so a kill aimed at mutate-changed (its process group, KILL included, or its name) leaves it to stop the checks, and it also stops them when its parent changes; a cut-off run's journal names its mutant and the checks' group, and recovery (the next run, or --recover) puts the file back, waits for those checks and names the group, and refuses while git holds the mutant anywhere it looks (HEAD, the index, a new stash and its index part, an operation's autostash, an autostash a merge left) or cannot tell; a journal a check removed is written again, and when it cannot be, the file is put back all the same and the line says no journal names it.
16. The method's hooks run only where Claude Code reads the repo's committed .claude/settings.json: in a local session and in a cloud session with one repository. A cloud session with several repositories runs no repo hooks, and a Projects cloud thread loads only CLAUDE.md (no hooks, skills, .mcp.json or repo settings); the owner's ~/.claude settings never reach the cloud (Claude Code docs, Nov 2026). Where the hooks do not run, nothing stops a commit or a merge in the session itself: CI and done-check are the net. Also, hook onFailure "block" has no effect on Stop hooks, so a gate at the end of a turn cannot rest on it. A client started in a subfolder of the project loads none of the project's hooks (measured; the harness keeps checking it, step 5.2). Reduced by step 5 (the hooks' README says where they do not run), M079 (one repo per code-changing cloud session), CI and done-check. When the guard itself is wrong, the owner switches the hooks off for one session: on their own computer with `--settings '{"disableAllHooks": true}'` or a local settings file made before the session starts; in a cloud session only by editing `.claude/settings.json` on GitHub's website on a branch and starting a new session on it, as Claude cannot (the hooks README says how). Since step 6, the method's rules have the main session say first that the hooks are off when no METHOD-ACTIVE line came, and change no code until the owner decides (M140), and `/method-start` says whether it saw that line; where the rules do not load either (a Projects thread), neither helps, and whether Claude acts on that text is convention (DECISIONS A73). Not closed: Claude Code decides what a cloud session loads.
17. The hooks cannot see the Claude Code version or the effort level at session start: Claude Code gives a hook neither (measured, 2.1.319), so session-status leaves both to /start, and the guard warns about effort at the first tool call (step 5). Since step 6.5, `/method-start` runs status.sh in full (its version area among the rest) and shows the session's effort through `${CLAUDE_EFFORT}`, saying first when it is not xhigh. Left: a session that never runs /method-start learns of an old client only from status run by hand.

18. gate-receipt (step 5b) is proven against the local fake Claude, not the real API: the auto-mode safety check, a handback's check warning, and the model, effort and token fields of a real API's agent record are taken as the pinned clients write them against the fake (measured at 2.1.316 and 2.1.319). A real record whose models or efforts take another form (another model id, an effort word that is not a level) makes receipts INVALID (model-off-list, effort-low), and one without them INCOMPLETE (no-model, no-effort); tokens are recorded, not checked, so usage under other names leaves a VALID receipt with zero tokens. Receipts, the write marks and the agent records are local files: a program Claude writes and runs can change them (RISKS #2), any write can change a gate's own agent record under `~/.claude/projects` (a plain `sed -i` or Edit, which G6 does not refuse there), and another gate's writes during a gate leave no mark. Reduced by the harness, which runs the real client on every change, and by step 9's live acceptance in a fresh cloud session. Left: what the real API writes, until step 9.

19. The method's rules, its agents' instructions and its skills are text (step 6): Claude can fail to follow one, and nothing notices. Reduced by `docs/method/why.md`, shipped with the method, which says which rules a hook or a script enforces, which are only partly checked (and what is not) and which are written down only (M067); by the gates, which check the work against the rules; by the prompt lint and the budgets, which keep the text short and plain (DECISIONS A73); and since step 6b by scripts that check what the rules ask for: done-check, which reads the gates' receipts and the task's plan (the owner's approval, the reviews and their rounds, the failing and passing runs, the reporter and Deep review, DECISIONS A74), and report-check, which finds every number of the report in the logs (M126). Left: a rule that is only written down is followed by convention, and the harness shows that the text reaches Claude, not that Claude acts on it; `/method-finish`'s own steps are such text, so a step it skips is seen only where done-check or report-check reads its result.

20. A Claude Code mod or plugin runs inside Claude Code, outside the method's hooks and checks: it can watch, change or refuse what Claude Code does, and a mod's hook that fails lets the action through (docs/research/README.md). Reduced (step 6b.4) by G6, which refuses Claude a write into the folders Claude Code loads mods and plugins from (`~/.claude/dev-mods/`, `~/.claude/plugins/`, also under `CLAUDE_CONFIG_DIR`); by G4, which refuses every `claude` command, `claude plugin install` too; by G16, which refuses a plugin enabled mid-session; by session-status, which names an enabled plugin as a LOOK line; and by the rule that method work uses no mods (M105), with why.md's "Not now" if Claude Code offers to turn on hot reloading for mods. Left: a mod or plugin the owner installs or loads (/plugin, --plugin-dir) is not stopped, and a program Claude writes and runs can still write into those folders (RISKS #2).

21. A first install of the method in a project is planned to be reviewed like any other change, in a fresh session started on its install branch, which loads the newly installed hooks and checking agents (DECISIONS A78, step 7). If such a session cannot start (whether it can is a step 9 fact), the owner decided on 23 November 2026 that the install may be merged on its card and check output alone, as a recorded exception to SPEC R4's floor: no gate receipts, no independent review and no security check, its pull request carrying `not-required - first install of the method <tag>`. Reduced by: it is used at most once per project, only with the owner's leave, and status names it; the install's files are the release's, which step 9's CI compares with the published tag. Left: that one change lands unreviewed.
