Nothing yet. Release 1 is being built. Release 1 will ship no ready-made packs for one field (such as ERPNext): the method fits any project, and each project can make its own pack (DECISIONS A77).

Step 8 (built, waiting for its review, CI and your merge, then the tag v0.8.0):
- This repository now runs the method's own hooks, from the first release, so any friction shows up here before it reaches your projects.
- The method can be taken back out of a project: `sync.sh --uninstall` shows its plan first, removes only what the method put there and nobody changed, and gives back your project as it was before the install. It names what stays. You run it in a session where the project's hooks are off, as you do an install; Claude can show you the plan but cannot write it.
- The method's scripts refuse to run when they were started by a bare name found elsewhere on your computer, because then they could have run the checked project's own helper code.
- Each session start now checks your own Claude Code folder for things that can quietly hide or replace the method in every project, and Claude tells you what to change and how, as only you can change that folder.
- Code Mode stays off in every project.
- The way to switch the hooks off for one session on your computer is a small settings file, which works in every shell.

Step 7 (merged on 26 November, released as v0.7.0) is the first step you will use in a project of your own:
- The method can now be put into a project. A tool called sync copies one release of the method in and keeps a fingerprint of every method file. If someone changes a method file by hand, the checks turn red and sync will not overwrite it.
- You set the project up by typing `/method-setup`. It asks six choice questions and a few short ones in your own words, shows you one screen of what your answers change, and writes the files only when you reply `write`. The same answers always give the same files.
- No answer can weaken the checks. Every change still gets the checks, an independent review and a security check.
- You choose a profile: Best results (the default), Balanced or Budget. A cheaper profile changes only the session you talk to. The checking agents stay on the strongest settings. A profile change takes effect from your next session.
- Your project's own rules go in its pack. Setup writes the first one from your answers. If a project rule conflicts with a method rule, the method rule wins. A change to the pack, the checks or the files that steer Claude needs three reviewers.
- Status tells you when your project's own always-loaded text passes 8,000 bytes, because long instructions are followed less well.
- A script that writes to real records outside the repository can use a small helper. It refuses to run without a stated reason, and only practises unless you say `--live`.
- If the project already has settings that could switch the method off or feed text to the checking agents, the first install stops and names them. You keep one only by naming it.
- The first install is reviewed like any other change, in a fresh session on its own branch. If that session cannot start, you may merge it without a review, once per project, as you decided on 23 November. Status names that commit.
- Three made-up example projects show it working: a word game, a small website and a records keeper.

After step 8 is merged, you create the tag v0.8.0 on GitHub, as you did v0.7.0. Claude gives you the exact steps.

### Added (step 5b)

- gate-receipt (step 5b.1), the method's third hook. It runs when one of the method's four checking agents (gates) starts or stops: method-reviewer, method-security-checker, method-diagnose and method-tester, matched by their exact names. At its start, a gate is told the line its report must end with: `END-VERDICT` and the id of the committed files it started on. Its report must open with one of its words: a verdict for the reviewer and the security checker, ROOT CAUSE, SYMPTOM CHASE or SPEC QUESTION for diagnose, TESTS PASS, TESTS FAIL or TESTS NOT RUN for the tester. A report without these two lines is sent back once with the exact lines it needs (in auto mode, its handback is refused once); a second miss is let go and recorded. Each gate run leaves a receipt in git's own folder: VALID, or INCOMPLETE (not checked) with a reason code. For now the receipt checks only the report's form: whether the files stayed the same, the model, the effort and the agent's instructions come in 5b.2, and nothing reads receipts until step 6. gate-receipt has no onFailure, so if it cannot run it never stops a gate or refuses its report.
- What you will see: one line per gate run in `.method/local/gates.log`, with the time, the receipt word, the gate, the files' tree id, the model (none until 5b.2), the effort and a reason code, never free text. A gate whose report lacks its lines gets one more turn, whose message starts `gate-receipt: your report must open with one of these words`.
- The verdict vocabulary (`verdicts.txt`) names the four gates and the words each report opens with, the three receipt words and the end key (DECISIONS A71).
- The review packet's header names the tree of the commit it shows (`Tree: <id>`, right after `HEAD: <id>`), so a review can be matched to the exact files it was made for.
- The log writer (`lib/log.pl`) also writes gates.log's lines, writes a file whole through a temporary file, and keeps the newest files of one kind by their exact time. The settings snapshot of step 5.9 now uses them. Before, a settings value with an accented letter made the snapshot unreadable, so a later settings change was judged the stricter way, as if no snapshot had been taken; that no longer happens. The newest 20 snapshots are kept, always the new one.
- The harness (step 5b.1) runs gate-receipt in the real client at both pinned versions, with the method's settings and a test-only stand-in reviewer gate: the start's line reaches only the gate; an agent named my-method-reviewer gets no gate-receipt hook; in default mode a complete report is VALID, a cut-off one is sent back once and then VALID, and one never completed is INCOMPLETE; in auto mode a handback without its lines is refused once, a second one is let through (INCOMPLETE), and a report given only as text is INCOMPLETE. It adds two client runs, about 5 s, at each version.
- Tests: 1 new test file (gate-receipt) and new cases in the vocabulary, packet, hook-helper, settings-change and settings tests; 3 new plant files (gate-receipt, the log writers, the packet) and new settings plants.; new harness cases (11 checks at each version: 9 gate questions and 2 safety lines) and 9 new harness plants.
- gate-receipt checks the evidence (step 5b.2). At a gate's start and stop it checks that the files are exactly the commit's (untracked files count) and that the commit's tree did not change. While a gate runs, the guard marks each call that writes, when the main session or an agent that is not a gate makes it (never the gate's own), and a mark in the gate's window makes the receipt INVALID. At the stop it reads the agent's record, waiting up to 5 s for it to be complete: every model must be on the project's availableModels, every turn's effort must be at least the method file's `effort:`, and the gate's instructions must be the method file's own text. The gate must not call another agent, work in another folder, leave a background shell running or review a packet built for other files. A reply the client wrote itself, a record that never completes or cannot be read, and files that cannot be told clean leave the receipt INCOMPLETE. The receipt keeps the models, efforts and tokens (each message counted once) for step 6.
- What you will see (step 5b.2): a receipt that says INVALID (the gate checked the wrong files or worked the wrong way) or INCOMPLETE (not checked), and its first reason code on its gates.log line, such as `write-mark`, `effort-low`, `model-off-list` or `record-late`. gates.log's model field names the first model the gate ran on (until now it said `none`). At each session's start, session-status names in one LOOK line the receipts for the files at HEAD that do not say VALID, for example `3 gate receipts for the files at HEAD do not say VALID: 1 INVALID, 2 INCOMPLETE (.method/local/gates.log says why)`.
- Measured on Linux: a gate's start takes about 0.3 s and its stop about 0.9 s on a 10,000-file repository with a 50 MB agent record (the plan's limit is 5 s). Every call that writes takes about 16 ms more in the guard, whether or not a gate runs; calls that only read are unchanged.
- The harness's other step 5b.2 cases run in the same default-mode run at both pinned versions: a gate whose Agent call asks for effort low, below its file's, is INVALID (effort-low); a gate run from a second definition of its name given on the command line (`--agents`) is INVALID (instructions-differ), and with a second project file of the name outside `.claude/agents/method/` the receipt follows the file the client ran; a receipt's models, efforts and tokens are the ones the client wrote in the gate's record. No new client run (about 1 s more at each version, about 20 s more in CI's harness job); 3 new harness checks at each version and 3 new harness plants.
- Tests: 43 new gate-receipt cases (87 in all), 14 guard cases, 5 hook-lib cases, 2 session-status cases; 64 new plants (gate-receipt 47, guard 12, log 3, session-status 2); the harness's gates.log question now expects the model read from the gate's record.
