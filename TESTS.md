# TESTS

Every check in this repo, and what runs it. What exists is not the same as what runs, so each row names its runner.

A check that has not been seen to fail is untested (M041). Every check below has planted defects in `tests/plants/dev-checks.sh` that must turn it red for its stated reason, and each check must stay green on a clean copy. Some checks also have a "looks close but is fine" case that must stay green, so a rule that fires too widely is caught too. Plants run in a throwaway copy of the repo, never in the working tree, so no plant can be left behind and no real work can be lost. Each plant that changes a file first confirms the change really landed before the check is run.

Rules every check follows:
- Text taken from a file name or file content is printed with control characters escaped (`\x0A`, `\x1B`, and UTF-8 C1 controls as `\xC2\x9B`), and with the CI runner's old command form `##[` broken up. Every line a check prints starts with the check's name; the mask filter, whose lines start with other tools' text, also breaks up `::` after any spaces, ASCII or Unicode. So a file cannot start a new line of output, move the cursor or send the CI runner a command.
- Each wrapper reads its helper's counts strictly: a count that is not one plain number is a failure, never a pass.
- Every check script clears the PERL_UNICODE and PERL5OPT settings, so perl reads bytes whatever the caller has set. One plant runs every check that prints file text, with `##[` and a C1 control in file names and content, under PERL_UNICODE=SDA.

## Known limits

- The secret scan reads the working-tree copies of the tracked files and the staged copies that differ, not git history. A secret added and removed within one push is not seen. A history scan is planned for Release 2.
- The portability lint is an early warning. It reads one line at a time and treats here-doc text as code, so it can miss a form split across lines and can flag text inside a here-doc. The real proof that the scripts run on bash 3.2 and BSD tools is the test suite on macOS, and on Git Bash it is the Windows run. Both run only on release tags and by hand (decision A19), neither has run yet (RISKS #9), and for now only Linux must pass (decision A27).
- No local bash 3.2 was available, so bash 3.2 behaviour has not been seen here.
- The secret scan misses many common credential forms. Checked misses: a quoted value under a bare TOKEN name (GITHUB_TOKEN="...", "NOTION_TOKEN": "..."), an unquoted YAML value (password: ...), a list item (- DB_PASSWORD=...), an Authorization Bearer header, a password in a URL (user:pass@host), .npmrc and .netrc entries, encryption_key, and key shapes such as sk_live_, glpat- and hf_. Closing these, and adding a second scanner, comes before the owner's files are imported (ROADMAP Track 3).
- In binary files the secret scan looks for keys and tokens, not for email addresses, phone numbers or IBANs.
- The secret scan accepts these misses so that ordinary text stays green: phone numbers written with dots (+1.415.555.0132); a phone number straight after `=` (phone=+14155550132); an IBAN run together with the next word (DE89370400440532013000BIC); UTF-16 without a byte-order mark when the text is mostly not ASCII.
- The portability lint misses an xargs `-r` that comes after an option with a quoted value (xargs -d '\n' -r). It flags every `$( )` that runs onto the next line, including valid ones.
- The rule-map check does not resolve `docs//rule-map.md` or `docs/../docs/rule-map.md` to the rule map.
- The workflow lint accepts only plain YAML, so it flags valid YAML it cannot read for sure: a flow mapping, an anchor, a quoted key, a value continued on the next line. Write such values as `key: value` on one line, or as a block scalar.
- Raw 8-bit C1 bytes that are not valid UTF-8 are not escaped. A UTF-8 terminal shows them as replacement characters.
- The plants that need a newline, a colon or an escape character in a file name are skipped on Windows, whose file system does not allow those names; so are the symlink tests where symlinks cannot be made.
- The workflow lint does not check `image:` under `container:` or `services:`, so a container image need not be pinned.
- perl -c runs BEGIN blocks of the perl files under `scripts/` and `method/scripts/`. That is this repo's own code, and anyone who can change it can change validate.sh too.
- A `-text` (binary) attribute in .gitattributes takes a file out of the line-endings check. Only a change to .gitattributes can do that, and such a change is reviewed like any other.
- An allowlist id can be reversed for a short value such as a phone number. The allowed text is in a tracked file of the same repo anyway, so the id reveals nothing new.

- The review packet lists a changed lockfile with its line counts only, so a swapped package source is seen only by opening the file (RISKS #11).
- A `.min.js` or `.min.css` file with a line of 500 bytes or more is left out of the packet's diff, whatever it holds.
- For a file stored in Git LFS, the packet shows the pointer git stored, and the reviewer reads the content from disk, which is checked against the SHA-256 the pointer names. That content counts only where the commit's own .gitattributes marks the path `filter=lfs` (with git 2.42 or later and a .git/info/attributes that holds no rule); otherwise a clone gets the pointer, so the content on disk is a change. A pointer with extension lines is refused. The tests use stand-in LFS filters and leave the user's and the system's git settings out, so they do not run the real git-lfs.
- The review packet has no size limit (DECISIONS A29): a large file or a big bundle is shown in full and can flood the reviewer. It also reads every tracked file once, to compare it with the commit, which takes longer in a very large repo.
- A file with its type's real signature and a NUL byte is shown as binary, in one line, even if it also holds text lines a shell could run. The same goes for any file left out of the diff as noise (a lockfile, a minified file, a source map that is also a script): a line elsewhere can run or load it, and that line shows in the diff.
- A file whose `working-tree-encoding` or `ident` attribute, or CRLF under `eol=lf`, comes from this machine (.git/info/attributes, a personal attributes file) and not from the commit's .gitattributes differs from the commit on disk, so the packet refuses it; one the commit's .gitattributes asks for is accepted (git 2.42 or later, and only while .git/info/attributes holds no rule). So does a file under a clean filter other than Git LFS (nbstripout, git-crypt), anywhere in the repo: in such a repo the packet refuses every change while the filtered files differ on disk.
- Lines added to a file that was already marked @generated at the merge base are left out of the diff with the rest of that file.
- review-packet.sh trusts the session it runs in: PATH, git and perl. A change to the builder itself, committed or hidden, is packaged by the changed builder (RISKS #11).
- In the packet, emoji joined with U+200D or ending in U+FE0F are shown as escapes, because those characters are also used to hide text.
- json.pl keeps the last of two equal keys, and prints a string that reads like another value ("true", "null", "12") the same way as that value. A module loaded through PERL5OPT (such as -MO=Deparse) runs before json.pl's first line, so its restart cannot undo it; a caller that cannot trust its environment unsets PERL5OPT first, as review-packet.sh does.
- The tests that run with only bash, git and perl on PATH link those tools into a folder. On Git Bash, where a link may be a copy without its libraries, they may need a different set-up when the Windows run happens.

- run-checks has no time limit per check: a check that never ends holds the run up (CI's job timeout stops it there).
- A count pattern is matched one output line at a time, so a count split over two lines is not seen.
- fresh-clone does not follow tracked symlinks under PRODUCT_PATHS, and tree-unchanged sees a change inside a submodule only as the submodule's status, so a second change inside an already changed submodule is not seen.
- run-checks' log and screen, and status's report, are written by the code being checked (RISKS #11).
- status reads CLAUDE_CODE_EFFORT_LEVEL from its own environment only, not from settings files (step 5's settings checks). It trusts the local refs: main's remote-tracking branch is as of the last fetch, and status never fetches. Its ci area takes gh's word for the runs.
- status's list of records is fixed in `lib/status.pl`; step 7's templates must match it.
- status and run-checks trust git's stat cache: an index whose stat data matches a changed file hides the edit until the file changes again, whether git refreshed it while a filter made the file look committed or someone wrote the index by hand. The review packet compares every tracked file with the commit, so a review still sees it, and the secret scan compares content itself.
- status's work area uses git's own comparison, which applies git's built-in conversions (core.autocrlf, the text and eol attributes, ident): an edit that only adds a CR to some lines (a CR at the end of `set -e` turns it off), or that a local ident attribute hides, looks committed there once `git add` or another refresh has run, and so does a CR on every line that a local core.autocrlf writes. run-checks' "tree at start" line and tree-unchanged, the packet and done-check compare the bytes (lib/tree.pl, DECISIONS A36). The review packet still accepts a file of up to 64 MB that differs from the commit only by CRs, as a checkout on Windows does, but names it in its header; run-checks counts it as uncommitted and done-check fails it.
- With every filter turned off, a Git LFS file whose stat data is out of date (touched, copied with new times, or written by a fresh clone in the same second as the index) shows as changed in status, run-checks and done-check until an ordinary git command refreshes the index. CI's fresh checkout is such a clone (step 9). The review packet builder still lets git run filter programs in its own `git status` (it then compares content itself).
- `safe.bareRepository` needs git 2.38 or later; older git ignores it, and then only the turned-off file-system monitor and filters keep a committed folder laid out like a repository from running anything.
- git freshens the time stamp of a split index's shared file (core.splitIndex) whenever it reads it, so status, run-checks, done-check and mutate-changed leave that one time stamp changed.
- On Windows, CLAUDE_CODE_EXECPATH is a `C:\` path that status does not treat as absolute, so the version floor is not checked there (reasoned from source; Windows is not run yet).
- status does not report files git ignores, also through this machine's own ignore settings; run-checks' fresh-clone check catches such files under PRODUCT_PATHS.
- Checks file names are shown escaped but not masked: they are project code, and a key used as a tracked file name already fails the secrets check. A malformed checks/scan-allow.txt, or one that is a link, makes the secrets check fail and show the reason; it does not stop the run before the checks, and status does not check that file. A REPOS entry is shown as written, escaped but not masked.
- Checks run in run-checks' own process group, so a check that signals its whole group (`trap 'kill 0' EXIT`) stops the run too; the log then has no END line, so the run counts as not run.
- tree-unchanged does not see a mode change git does not compare (core.fileMode=false, the default on Git Bash), or an edit inside an untracked nested repository, which git lists as one folder.
- The mask works line by line. It masks a private key (also an armored PGP one) from its BEGIN line to its END line, and key body lines just before an END line, but not a key whose shown window holds neither (the output was cut on both sides of it), and not other secrets spread over several lines. A BEGIN line with no END line masks the rest of that output, so a test that quotes such a line hides its own failure reason (it fails safe). A key split by a CR, a backspace, a NUL byte or an 8-bit CSI is shown escaped with all its characters. Keys and tokens are masked wherever they stand, also glued to a word; a phone number, IBAN, email address or credential right after an escape in a spelling the mask does not split at (`%1B`, `&#27;`, `\x9b`) is shown.
- The file scan does not join a key split by codes written as text (the mask does). In a file that holds a NUL byte, searched for keys only, escapes written as text are not split, so a key right after one is missed. Past 100 finds on one line, a find that a piece of the line holds in part is reported again. On a checkout with CRLF line ends (core.autocrlf, the default on Git for Windows), and on a sparse checkout, the scan reads the staged copy of every such file too: the same finds, in up to twice the time. A key glued to a letter after an ESC spelling the scan does not split (`\x1b7`, `\x1bM`, `\N{ESC}`, `%1B`, `&#27;`, PowerShell's `` `e ``, `\x9b`) is missed, and so is an env-style credential right after `\n` written as text (a printf that writes a .env file, .env text in a string), which would otherwise bring false alarms from code in strings.
- The mask shows a key split by `\n` or `\t` written as text in its pieces, and the removed lines of a key file's diff when the window does not hold the key's BEGIN line.
- Git::flagged and the submodule walk stop at 8 levels of nesting, and cost three git runs per submodule, so status is slower in a project with very many submodules.
- A tracked file that is missing from disk and marked skip-worktree is a LOOK in status, and run-checks says "on uncommitted changes", also in a real sparse checkout: tests outside the sparse set do not run there.
- Run from a linked worktree of a repository whose git folder is not a `.git` folder in its main working tree (a submodule, --separate-git-dir, a `.git` that is a symlink), status cannot find the main working tree (git lists the repository's own folder for it), so the work area is a LOOK saying git ls-files failed. Run in a copy of a linked worktree, status reads the folder git lists, not the copy.
- A count pattern can backtrack for a very long time on one output line (nested repeats), and run-checks has no time limit per check.
- status reads VERDICTS_FROM from the working tree, so a task branch can move it before the change is reviewed; done-check checks such a change at merge (its verdicts start condition, DECISIONS A37).
- Only GitHub's runner command forms (`##[`, and `::` at the start of a line) are broken up; Azure Pipelines' `##vso[` and TeamCity's `##teamcity[` pass through. The method's CI is GitHub (step 9).

- done-check's READY rests on local claims until CI runs the checks (step 9) and review receipts replace the verdict line (step 5): the run-checks log sits in a git-ignored folder anyone in the session can write, and the verdict line is typed by the author. done-check, its libraries and its inputs (checks/*.tsv, .claude/method.conf, checks/scan-allow.txt, verdicts.txt) run from the change, so a change to them grades itself until the base branch's done-check runs in CI (M118, Release 2; RISKS #11).
- A rebase, an amend or a cherry-pick carries an approving verdict line onto a version nobody reviewed, and done-check cannot tell that from the line (receipts at the exact files, step 5, M106).
- A project check whose result depends on commit messages or history counts as covered by a run of the same files at an amended twin or at an ancestor (DECISIONS A35).
- done-check assumes a squash merge, or a merge commit, that carries HEAD's verdict line as its last paragraph (A30). A fast-forward or rebase merge puts every branch commit on main, where status then judges each one; that is not supported (steps 7 and 9 set squash-only).
- A project with a check that runs only in CI is never READY locally until done-check reads CI's result (step 9), and one with a local-only check is never READY under CI=true (DECISIONS A34).
- The conversions done-check, run-checks and the packet accept, and the Git LFS content they accept, need git 2.42 or later and a `.git/info/attributes` that holds no rule; otherwise a committed `eol=crlf`, `ident` or `working-tree-encoding` file, and LFS content, always differ, and done-check says why. A checkout whose CRLF comes from this machine's settings (core.autocrlf, the Windows default; core.eol; `.git/info/attributes`) counts as changed (A27).
- Each file that differs from its stored bytes, a file the commit converts included, costs one git run to get the bytes git's checkout writes: in a project that commits `* text eol=crlf`, 2000 text files take about 12 seconds per done-check and twice that per run-checks on Linux.
- A file under a filter other than Git LFS (git-crypt, nbstripout) always differs from the commit, so done-check is never READY in such a project.
- A tracked file over 64 MB that differs from the commit is not read whole: it counts as edited, also when only its line ends differ.
- On git older than 2.44, reading an object a partial clone lacks fetches it (GIT_NO_LAZY_FETCH is newer), so done-check and the other tools may reach the network there.
- done-check does not judge files git ignores: ignored files under PRODUCT_PATHS are fresh-clone's job, the rest CI's clean checkout (step 9). An ignore rule that is not in the commit (.git/info/exclude, core.excludesFile, an untracked folder's own .gitignore) can hide an untracked helper outside PRODUCT_PATHS.
- git never lists an untracked folder named .git inside a tracked folder, so the files condition, tree-unchanged and fresh-clone do not see it or the files in it.
- core.ignoreCase is pinned to false only where the working tree's file system tells case apart: Git::case_pin asks whether the top folder and its name with the case flipped, in the folder above, are one folder. Where they are (macOS, Windows), git's own setting stays, so ignore and attribute patterns match as git matches them. That side is simulated here with a symlink, not run on macOS or Windows (A27). A symlink made on purpose next to the top folder turns the pin off; that takes the author agent (RISKS #11). A top folder whose name has no letters keeps the pin, and one that is itself the root of a volume is judged by the volume above it. Git::cat and secrets.pl call git without the pin; their commands do not read core.ignoreCase.
- Only the newest 20 run-checks logs are kept, so done-check names earlier failed runs of the same files only among those.
- mutate-changed's mutants are text changes (DECISIONS A40). A comparison written without spaces is still mutated, but a lone < or >, binary + and -, and an operator only a language of its own has are not; a line is comment-like by its first characters only, so a code line that starts with * or -- is skipped, and a comment after code is mutated. Equivalent mutants (a change that does not change what the code does) will survive when mutants run (step 4b.3).
- The method's own scripts are never mutated (the folder mutate-changed.sh runs from); in this repo the rest is reachable when MUTATE_PATHS covers it (scripts/dev/, the test scripts that delete nothing, .github/, and the records and docs, whose prose and numbers get mutants that survive). This repo's evidence for its own tests stays the planted-break runs.
- mutate-changed's guard against mutants that delete, move or overwrite files is a fixed list of words, not a parser (mutate-changed.sh's header names them; RISKS #13): a shell script, make file or batch file with a line that names one is skipped whole, any other file only on that line. A delete, move or overwrite written any other way (a command or call not on the list, such as cp over a file or a helper of the project's own, or a command split over lines without a line-end backslash, or ^ or ` in a batch file) gets mutants, even on the line with its guard; outside shell, make and batch files a guard on another line than its delete gets mutants, unless a line-end backslash joins the two. The list also matches more than deletes (a comment or a name holding one of the words, Python's del): such lines get no mutant and are counted, so naming a word keeps a line out of the plan.
- The plan shows the numbers 0 and 1 as they are and any other number only by its length. FILE:LINE:COLUMN on the screen is ambiguous for a file name that holds a colon (step 6 reads plans back by id). A last line that only gains its line end counts as added (git's line diff), so its old text can get a mutant. A Markdown table's || is mutated like the operator.
- done-check trusts the local refs: main is as of the last fetch, and done-check never fetches; main's ref counts only when the remote's fetch settings name it. With no remote (one with a URL) and no remote-tracking branch at all, main is the local main or master. In a fork layout (origin is the fork, upstream the real repository), main is the fork's main. A git-svn or git-p4 clone (remote-tracking branches, no remote) has no main here, and its advice to add a remote does not apply.
- A project that keeps .claude/method.conf in a submodule, in Git LFS or under a filter or an encoding, on main or in the change, is never READY: main's VERDICTS_FROM cannot be read as status reads it, so even the change that makes it a plain file could not be checked (compare with status on main). With git older than 2.42, or rules in .git/info/attributes, a .gitattributes on the path that mentions a filter, an encoding or a macro is enough to refuse (also an LFS rule for other files). A driver literally named unspecified or unset, and a .GITATTRIBUTES whose case differs on a file system that folds case, are not seen.
- A file that still holds the stored bytes counts as the commit even when the commit's own .gitattributes asks for a conversion (an eol rule added in the change, or kept off by a `-text` rule in .git/info/attributes): a fresh clone gets other bytes, which CI's clean checkout sees (step 9; DECISIONS A36).
- The executable bit is not compared under core.fileMode=false (the Git Bash default, or set by hand), so a script that runs here can fail in a clone with "Permission denied".
- With core.symlinks=false (Git for Windows without symlinks), git writes a committed symlink as a plain file holding its target; the packet refuses such a checkout and done-check is never READY, and its "next:" advice cannot fix it (DECISIONS A36, A27).
- A submodule is compared with the commit its parent records only when it is checked out; nesting deeper than 8 levels is not compared, and a filter program set only inside such a deep submodule can still run when git status reads it. So can one set inside a submodule nested in a submodule whose .git points at another folder (Git::submodules does not walk into it); done-check is NOT READY there, since the outer submodule fails files.
- A clone of a working copy that is on a task branch, or `git remote set-head`, points origin/HEAD at that branch; on any other branch, done-check then takes it as main. Both lines that use main name it.
- On the default branch itself, when it is neither main nor master (git-flow's develop), done-check skips origin/HEAD as HEAD's own branch and takes origin's main or master instead, so up to date is judged against that branch. Both lines that use main name it.
- Deleting or renaming a run-checks log removes a failed run from what done-check reads (RISKS #11).
- The limited runner stops what stays in a check's process group: a process that starts its own group or session (setsid, setpgid, a detached spawn, a container) is not stopped, nor is what a check left behind when a harness kills the whole process tree, the watchdog with it (RISKS #14). A check that the terminal stops (it reads /dev/tty from a background group) is found only by its time limit. On NFS, the watchdog of a cut-off mutate run does not hold the lock (flock there is per process).
- status looks for a mutate-changed run (its lock and journal) in the working tree it reports on, not in each linked worktree.
- A check can stop or kill its own watchdog: stopped, it keeps the lock held until someone kills it (run-checks says busy, recovery waits); killed, it leaves the check unguarded (RISKS #14). The lock's type is checked before it is opened and again after, so a FIFO swapped in between is still named; that second check, the TERM and fast KILL going only to a group still there, and take's refusal of a link where O_NOFOLLOW is missing (Linux, macOS and Cygwin have it) cannot be timed or reached in a test: reasoned, not planted.
- run-checks and mutate-changed need git's folder to be writable and to support flock: a read-only git folder, or a file system without locks, stops them (exit 2) where run-checks used to run.
- A run of mutants trusts what the checks report: a kill can be code that no longer loads, a flaky check kills at random, and an equivalent mutant (or one in a string or comment-like text the plan cannot tell) survives; step 4b.4 adds the repeat and control runs, step 6 the accept path. A cache keyed on a file's path alone, a watcher or a dev server, sees mutants. Files put back are newer than any build, so a "build is current" check fails until a rebuild. The per-mutant compare costs one fingerprint (done-check's cost, D3). The write function keeps the mode, not ACLs, extended attributes, the owner or hard links; a file it writes can be up to about 3 s ahead of the clock, which make may warn about. A check that rewrites refs/stash to the id it had at the start hides a stash made in between. When mutate-changed and its watchdog are both killed in the instant after a check starts, the journal names no group, and recovery cannot wait for that check (RISKS #14). Recovery checks HEAD, the index and stashes made during the run, not older commits or pushed branches: a mutant committed and then changed again later stays in history. On Windows, a rename over a file another program holds open fails (exit 2, the journal stays), and Git Bash's group kill reaches only its own processes (reasoned, A27). The fsync before each rename, and the journal written before the mutant, matter only for a power loss or a kill in that instant; a signal that lands after a round's last check, or between rounds, is looked at before the next mutant and before the last line, a window no test can hit on time: reasoned, not tested.

## Where CI runs

- Linux: every push and pull request (a 25-minute limit: the whole suite takes about 11 minutes, mutate-run's 30 s time-limit case and its signals among it). Windows and macOS jobs have 30 minutes.
- Windows (Git Bash) and macOS: release tags and manual runs (decision A19).
- Each run step first sends `::stop-commands::` with a random token, so the runner reads no workflow commands from the output that follows. A manual run and a push run on the same branch use different concurrency groups, so neither cancels the other.
