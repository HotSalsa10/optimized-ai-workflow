# TESTS

Every check in this repo, and what runs it. What exists is not the same as what runs, so each row names its runner.

A check that has not been seen to fail is untested (M041). Every check below has planted defects in `tests/plants/dev-checks.sh` that must turn it red for its stated reason, and each check must stay green on a clean copy. Some checks also have a "looks close but is fine" case that must stay green, so a rule that fires too widely is caught too. Plants run in a throwaway copy of the repo, never in the working tree, so no plant can be left behind and no real work can be lost. Each plant that changes a file first confirms the change really landed before the check is run.

Rules every check follows:
- Text taken from a file name or file content is printed with control characters escaped (`\x0A`, `\x1B`, and UTF-8 C1 controls as `\xC2\x9B`), and with the CI runner's old command form `##[` broken up. Every line a check prints starts with the check's name; the mask filter, whose lines start with other tools' text, also breaks up `::` after any spaces, ASCII or Unicode. So a file cannot start a new line of output, move the cursor or send the CI runner a command.
- Each wrapper reads its helper's counts strictly: a count that is not one plain number is a failure, never a pass.
- Every check script clears the PERL_UNICODE and PERL5OPT settings, so perl reads bytes whatever the caller has set. One plant runs every check that prints file text, with `##[` and a C1 control in file names and content, under PERL_UNICODE=SDA.

## Planted breaks

To check the checks, each guard was removed once in a throwaway copy, and the full test suite was run against it (in step 2's last two runs, the tests of the file it changed).
- Step 1b, with its three repair loops, run again on the final code: 101 removals. 98 turned the suite red. The other 3 change no behaviour, so no test can catch them: the allowlist's lookup by path (the id already includes the path); the `./` before perl file names (every name already starts with `scripts/`); and an older way of reading a comment after a job key (the comment is now handled before that code runs).
- The first run after repair loop 3 found 8 more removals that the suite missed. Each was resolved before the final run:
  - 5 are now caught: the PERL_UNICODE clearing in the secret scan and in the workflow lint (a plant now uses file names holding a C1 control, under PERL_UNICODE=SDA); keeping such names away from perl (a planted perl file that does not compile must not fail perl-syntax); and two removals of the call that scans tracked names (file names are now scanned in one place, so the plants for keys in file names depend on it).
  - 3 tested code that only repeated other code, so that code was removed: the extra calls that scanned the same file names again, the names check's own `##[` break-up (the mask filter does it), and `--` before ln in the sandbox (targets starting with `-` are refused before ln runs).
- Step 1: 21 of its 27 removals still apply, and all are caught. The other 6 targeted code that step 1b rewrote; their counterparts are among the 101.
- Every portability rule was deleted in turn during step 1, and each deletion was caught; the rules have not changed since.
- Step 2, run again after repair loop 3: 148 removals, each run against the tests of the file it changed. 144 turned the tests red (one, the check that a file is a regular file, by its time limit: the packet would wait on a FIFO). The other 4 cannot be caught here: JSON::PP's `allow_nonref` (on by default in JSON::PP 4); the packet's refusal when git shows no change for two different stored versions (git always shows one while `--text` is passed); its check that a file that opened could also be read; and `--literal-pathspecs` (no git call takes a pathspec).

## Known limits

- The secret scan reads the working-tree copies of the tracked files and the staged copies that differ, not git history. A secret added and removed within one push is not seen. A history scan is planned for Release 2.
- The portability lint is an early warning. It reads one line at a time and treats here-doc text as code, so it can miss a form split across lines and can flag text inside a here-doc. The real proof that the scripts run on bash 3.2 and BSD tools is the test suite on macOS, and on Git Bash it is the Windows run. Both run only on release tags and by hand (decision A19), neither has run yet (RISKS #9), and for now only Linux must pass (decision A27).
- No local bash 3.2 was available, so bash 3.2 behaviour has not been seen here.
- The secret scan misses many common credential forms. Checked misses: a quoted value under a bare TOKEN name (GITHUB_TOKEN="...", "NOTION_TOKEN": "..."), an unquoted YAML value (password: ...), a list item (- DB_PASSWORD=...), an Authorization Bearer header, a password in a URL (user:pass@host), .npmrc and .netrc entries, encryption_key, and key shapes such as sk_live_, glpat- and hf_. Closing these, and adding a second scanner, comes before the owner's files are imported (ROADMAP Track 3).
- In binary files the secret scan looks for keys and tokens, not for email addresses, phone numbers or IBANs.
- The secret scan accepts these misses so that ordinary text stays green: phone numbers written with dots (+1.415.555.0132); a phone number straight after `=` (phone=+14155550132); an IBAN run together with the next word (DE89370400440532013000BIC); UTF-16 without a byte-order mark when the text is mostly not ASCII.
- The portability lint misses an xargs `-r` that comes after an option with a quoted value (xargs -d '\n' -r). It flags every `$( )` that runs onto the next line, including valid ones.
- The rule-map check does not resolve `docs//rule-map.md` or `docs/../docs/rule-map.md` to the rule map.
- The workflow lint accepts only plain YAML, so it flags valid YAML it cannot read for sure: a flow mapping, an anchor, a quoted key, a value continued on the next line. Write such values as `key: value` on one line, or as a block scalar.
- Raw 8-bit C1 bytes that are not valid UTF-8 are not escaped. A UTF-8 terminal shows them as replacement characters.
- The plants that need a newline, a colon or an escape character in a file name are skipped on Windows, whose file system does not allow those names; so are the symlink tests where symlinks cannot be made.
- The workflow lint does not check `image:` under `container:` or `services:`, so a container image need not be pinned.
- perl -c runs BEGIN blocks of the perl files under `scripts/` and `method/scripts/`. That is this repo's own code, and anyone who can change it can change validate.sh too.
- A `-text` (binary) attribute in .gitattributes takes a file out of the line-endings check. Only a change to .gitattributes can do that, and such a change is reviewed like any other.
- An allowlist id can be reversed for a short value such as a phone number. The allowed text is in a tracked file of the same repo anyway, so the id reveals nothing new.

- The review packet lists a changed lockfile with its line counts only, so a swapped package source is seen only by opening the file (RISKS #11).
- A `.min.js` or `.min.css` file with a line of 500 bytes or more is left out of the packet's diff, whatever it holds.
- For a file stored in Git LFS, the packet shows the pointer git stored, and the reviewer reads the content from disk, which is checked against the SHA-256 the pointer names. A pointer with extension lines is refused. The tests use stand-in LFS filters and leave the user's and the system's git settings out, so they do not run the real git-lfs.
- The review packet has no size limit (DECISIONS A29): a large file or a big bundle is shown in full and can flood the reviewer. It also reads every tracked file once, to compare it with the commit, which takes longer in a very large repo.
- A file with its type's real signature and a NUL byte is shown as binary, in one line, even if it also holds text lines a shell could run. The same goes for any file left out of the diff as noise (a lockfile, a minified file, a source map that is also a script): a line elsewhere can run or load it, and that line shows in the diff.
- A file with a `working-tree-encoding` or `ident` attribute, or a CRLF file stored under `eol=lf`, differs from the commit on disk, so the packet refuses it. So does a file under a clean filter other than Git LFS (nbstripout, git-crypt), anywhere in the repo: in such a repo the packet refuses every change while the filtered files differ on disk.
- Lines added to a file that was already marked @generated at the merge base are left out of the diff with the rest of that file.
- review-packet.sh trusts the session it runs in: PATH, git and perl. A change to the builder itself, committed or hidden, is packaged by the changed builder (RISKS #11).
- In the packet, emoji joined with U+200D or ending in U+FE0F are shown as escapes, because those characters are also used to hide text.
- json.pl keeps the last of two equal keys, and prints a string that reads like another value ("true", "null", "12") the same way as that value. A module loaded through PERL5OPT (such as -MO=Deparse) runs before json.pl's first line, so its restart cannot undo it; a caller that cannot trust its environment unsets PERL5OPT first, as review-packet.sh does.
- The tests that run with only bash, git and perl on PATH link those tools into a folder. On Git Bash, where a link may be a copy without its libraries, they may need a different set-up when the Windows run happens.

## Where CI runs

- Linux: every push and pull request.
- Windows (Git Bash) and macOS: release tags and manual runs (decision A19).
- Each run step first sends `::stop-commands::` with a random token, so the runner reads no workflow commands from the output that follows. A manual run and a push run on the same branch use different concurrency groups, so neither cancels the other.
